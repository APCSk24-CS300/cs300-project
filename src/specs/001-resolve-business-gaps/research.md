# Documentation Decisions

| Decision | Rationale | Alternative considered |
| --- | --- | --- |
| Preserve the original heading hierarchy and section order. | The user explicitly requested the old layout. | Replacing the document with a new requirements outline would obscure the original review context. |
| Edit conflicting entity rows, cardinalities, and constraints in place. | A gap is closed only when all active statements in the document agree. | A superseding addendum would leave contradictory text in the same file. |
| Add required entities as rows under existing tables. | The existing Schema design section already contains the relevant entity categories. | New entity sections would change the document structure. |
| Keep unresolved policy choices identified as assumptions pending stakeholder review. | The constitution requires consultation before architecture departures and review before implementation. | Treating an inferred rule as approved would overstate its authority. |
| Do not create software deliverables or tests. | This request is limited to Markdown business requirements. | The previous service implementation plan exceeded the user's scope. |

The gap analysis is the traceability source for DB-01 through DB-18. The project proposal is the baseline for supported product behavior.
