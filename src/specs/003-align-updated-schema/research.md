# Research: Align Updated Business Schema

The updated business requirements are the source of truth. A small `Major` reference table supports the documented nullable `Student.major_id` foreign key without leaving a dangling reference. The current `db/schema.sql` has 28 tables, including `RefreshToken` and `SystemSetting`; comparison with the business entity tables identifies 17 missing business entities plus the older `ActivityOrganizer` name. This is an initial-schema edit, not a migration for populated installations.

## Decisions

| Decision | Rationale | Alternative considered |
| --- | --- | --- |
| Keep the current script order and edit table definitions in place; insert missing entity tables near related existing tables. | Preserves the recognizable design and confines the product diff to `db/schema.sql`. | Rebuild or reorder the entire script, which exceeds the requested scope. |
| Keep `RefreshToken` byte-for-byte unchanged. | The user explicitly reserves this backend table; the current block can be validated as part of the full script without edits. | Rebuilding backend token storage, which the user prohibited. |
| Replace one-role-per-user storage with `UserRole` and role-matched profile tables; retain `Role` and `RolePermission`. | Allows independent duties and scoped assignments without implicit permission inheritance. | Multiple Boolean flags or cumulative role hierarchy, which conflicts with the updated requirements. |
| Retain `ActivityOrganizer`'s two-column assignment shape while aligning its business meaning to `ActivityManage`; add organization ownership and membership separately. | Minimizes structural disruption to existing activity links. | A new parallel manager-assignment table with duplicate authority. |
| Use a partial unique index for one active registration per activity and student, keeping terminal attempts. | A global unique key prevents valid re-registration after rejection or cancellation. PostgreSQL supports subset uniqueness through partial unique indexes. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | Keep the current `UNIQUE(activity_id,user_id)`, which conflicts with the requirements. |
| Preserve the composite foreign-key pattern tying Attendance to the same activity as both Schedule and Registration. | This is already a sound cross-record integrity pattern; referenced column pairs must remain unique. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | A row-local `CHECK` comparing other tables, which is not a valid way to enforce cross-table state. |
| Represent scoring versions with a stable version key and explicit criterion and semester links; use foreign keys and unique keys where equality can be encoded. | Historical awards keep their applied policy; row-local `CHECK` rules should not pretend to inspect other rows. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | Replacing criteria on policy changes, which would lose award provenance. |
| Put simple domains, keys, uniqueness, and source exclusivity in SQL; identify multi-row authorization, transitions, queue promotion, capacity counts, notification creation, and atomic decision effects as workflow or transaction obligations unless a focused SQL mechanism is justified. | These rules depend on actor, time, or several records and cannot be made true with a local `CHECK`. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | Broad trigger machinery in this schema-only change, which would substantially alter its design. |
| Validate the full file on an isolated disposable database and report its actual result. | `psql -v ON_ERROR_STOP=1` stops at the first error and can validate the untouched backend table along with the aligned schema. [PostgreSQL psql](https://www.postgresql.org/docs/current/app-psql.html) | Prefix-only execution, which would leave the final table unvalidated. |

## Boundary and open policy

The business requirements themselves label several decisions provisional: role combinations, one owner, pending seat reservation, repeat registration, displacement priority, and weighted scoring. This plan implements their documented schema representation without presenting stakeholder policy approval as complete. A reviewed specification is required before implementation under Constitution III. No `NEEDS CLARIFICATION` item remains for planning.
